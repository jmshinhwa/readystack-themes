# SEPA pain.001 Reject Lint

![SEPA pain.001 Reject Lint](https://getreadystack.com/img/promo/sku96106_result_card.jpg)

A SEPA credit transfer file is accepted or returned before a human reads it. The bank's
gateway parses the XML, applies the scheme rules, and sends the whole batch back if one
transaction breaks one of them. Everything in the batch waits, including the invoices
that were due that day.

This extension reads a `pain.001` file the way that gateway does and marks the lines that
will be refused, with the reason and the line number.

## What it checks

25 rules, all of them checkable from the file alone:

**Message version and envelope**
- The namespace is the 2019 ISO 20022 version `pain.001.001.09`, not one of the retired
  2009 versions `pain.001.001.03` through `.08`. This is the single most common finding in
  files produced from an old template or generated by a model trained on old examples.
- `<?xml ... encoding="UTF-8"?>`
- `GrpHdr/CreDtTm` is a real ISO 8601 date-time
- `MsgId`, `PmtInfId`, `InstrId` and `EndToEndId` stay inside 35 characters

**Scheme fields**
- `PmtTpInf/SvcLvl/Cd` is `SEPA` or `INST`
- `ChrgBr` is `SLEV`
- `ReqdExctnDt` is wrapped as `ReqdExctnDt/Dt` (the 2019 shape), and is not already in the past

**Accounts and parties**
- Every IBAN passes the ISO 7064 mod-97 check
- Every IBAN country code is inside the SEPA area
- Every BIC matches the ISO 9362 shape (8 or 11 characters)
- No party name runs past 70 characters

**Amounts**
- `InstdAmt` currency is EUR, the value is positive and has at most two decimals
- `CtrlSum` equals the sum of the instructed amounts in the file
- `NbOfTxs` equals the number of `CdtTrfTxInf` blocks
- An instant transfer parked just under 100000 EUR is flagged: the old SCT Inst amount cap
  was lifted by the Instant Payments Regulation, so splitting a payment to stay under it is
  work nobody has to do any more

**Remittance and identifiers**
- `RmtInf/Ustrd` stays inside 140 characters
- A structured creditor reference beginning `RF` passes the ISO 11649 mod-97 check
- No `EndToEndId` repeats inside the same message
- Every character in a name, address, remittance line or identifier belongs to the SEPA
  Latin set: `a-z A-Z 0-9 / - ? : ( ) . , ' +` and space. An umlaut, an ampersand or a
  smart quote pasted from a supplier's invoice is enough to have the file refused.

## How to run it

Open a `pain.001` XML file and run **SEPA pain.001: Check this file** from the command
palette. Findings arrive in the Problems panel on the line that causes them. The same
engine runs on the free web page with nothing installed.

## What this is not

It is not an XSD validator. A file can be schema-valid and still be returned: the schema
has no opinion about whether `CtrlSum` adds up, whether the IBAN checksum holds, or whether
the message is the version the scheme is carrying this year.

By hand, this is 25 rule checks per transaction, read against the rulebook, every time the
batch changes.

## Where the rules come from

The EPC SEPA Credit Transfer scheme rulebook and implementation guidelines, the ISO 20022
`pain.001.001.09` message definition, ISO 7064 (IBAN check digits), ISO 11649 (structured
creditor reference) and ISO 9362 (BIC). Each rule carries its identifier in the finding, so
a finding can be traced back to the clause it comes from.
